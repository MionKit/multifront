# Milestone 6.1: Fixes and groundwork before full editor support

## Goal

Close what milestone 6 left open, and set the command-line rules milestone 7 builds on, before milestone 7 starts.

- Tests give the same answer from any folder.
- A library never ships two files whose names differ only by case.
- A parent styles one `.ucf` component the same way from React, Vue and Svelte (`class` / `className`, `style`).
- Every multifront command works well for coding agents: check one file, read a machine format, get a clear exit code.
  `mf-build` follows these rules now; milestone 7 plans `mf-tsc`, `mf-lint` and `mf-fmt` with them from the start.

## Steps

The four topics share no code at their start, but some touch the same files (6.1.1 and 6.1.3 the Svelte block
snapshots, 6.1.2 and 6.1.3 `dts.ts`). Steps run one at a time, in this order: smallest and most isolated first.

### 6.1.1 Svelte block tests give the same result from any folder

- Build: `serverModule` in `packages/core/test/svelte/render.ts` compiles with
  `filename: ctx.filename + '.svelte.svelte'`. Svelte hashes the `<svelte:head>` comment from that filename relative
  to its `rootDir` option, which defaults to `process.cwd()`. So "renders every element from the block with the scope
  once and only module class names" fails for `svelte/shapes/SpecialElements.ucf` when vitest starts from
  `packages/core` (`<!--19p0f6f-->` vs `<!--hxl29t-->`), and passes from the repo root. Likely fix: a fixed `rootDir`
  (repo root or fixtures folder) on that `compile` call. The step confirms the cause first.
- Deliverable: the core block tests pass the same from `packages/core` and from the repo root, snapshot unchanged.
- Test: run `packages/core/test/blocks/svelte.spec.ts` from both folders (`pnpm exec vitest run
  test/blocks/svelte.spec.ts` in `packages/core`, `pnpm devx test` at the root). Both green, no snapshot update.
- Docs: none, test-only.
- Status: done

### 6.1.2 Output names that differ only by case are a build error

- Build: the three name clash checks of `buildLibrary()` compare output names case-insensitively. Today
  `src/icon.svelte.ts` beside `src/Icon.ucf`, or `src/card.ts` beside `src/Card.ucf`, builds green on Linux; on
  macOS or Windows (case-insensitive file systems) one file overwrites the other once installed. The error keeps
  both names as written. The plan decides whether a case-only clash reuses `... would both be written as ...` or
  gets a message of its own.
- Deliverable: a case-only clash fails every check, on every OS.
- Test: build area, beside the existing clash cases in `packages/e2e/build/library.spec.ts` (two chunks) and
  `packages/e2e/build/svelte-library.spec.ts` (plain Svelte file, `.svelte.ts` module): one fixture library copy per
  check with a case-only clash, each failing with the exact message.
- Docs: `docs/milestones/m6-library-build.md` (6.1 and 6.8 build errors) and the error table of
  `publicdocs/06-building-a-library.md`, if the message changes.

### 6.1.3 Svelte roots take `class` and `style`

- Build: every forwarded Svelte root accepts and merges `class` and `style` the way React roots merge `className`
  and `style`: classes joined, the parent's style keys win. "The author wins" as in React: a component that reads
  the prop itself keeps it. Built on the Svelte root forwarding in `packages/core/src/blocks/svelte.ts` and the shared
  helper module (`packages/core/src/react/scopeHelper.ts`). Types follow: the Svelte virtual script and the library
  `.d.ts` gain `class?` and `style?`, as React's props type does through `reactRootProps()`. The plan settles helper
  names, legacy-mode components and multi-root rules.
- Deliverable: a parent passes a class and a style to the same `.ucf` component from Svelte as from React and Vue,
  in an app and through the library build, with editor and `.d.ts` types.
- Test:
  - build and browser areas: a Svelte fixture parent passes `class` and `style` to a `.ucf` child; computed styles
    in Chromium match the React and Vue runs of the same fixture.
  - editor area: the Svelte virtual script accepts `class` and `style` on the component, tsserver with our plugin
    reports no error; a wrong type (`style={1}`) is an error.
  - consumer area: `packages/e2e/fixtures/apps/consumer-sveltekit/` passes `class` and `style` to Button like the
    other three apps; `packages/e2e/consumer/exit.spec.ts` drops its `target !== 'svelte'` skip.
- Docs: `docs/spec.md` section 3 (Svelte transform gets the merge of 3.5 item 5) and section 8 ("React conventions"
  becomes one styling rule for every framework); `docs/architecture.md` (the helper module's root-prop merges cover
  Svelte); `publicdocs/03-styles.md` (its root forwarding table says Svelte roots take `class` and `style`).

### 6.1.4 Style features audit across the three frameworks

- Build: list every style feature and check each in React, Vue and Svelte: `<style module>`, `<style scoped>`,
  preprocessors, CSS variables, `:deep()` / `:global()` / `:slotted()`, `v-bind()` in CSS, a parent's scoped style
  reaching a child root, styling of content passed in through slot / children / snippet. Close each gap here; a big
  gap becomes its own todo. The spec's open question on `v-bind()` in CSS for React and Svelte gets an answer.
  JavaScript side, check only: props, element refs (React `ref`, Vue template ref, Svelte `bind:this`) and slots /
  children / snippets keep each framework's own way; fix what is broken, add nothing to make them look alike.
- Deliverable: the audit table (feature by framework: works, fixed here, or its own todo) in `docs/spec.md`.
- Test: browser area, one fixture per feature group rendered in all three frameworks, computed styles compared.
  Props, refs and slots: one render test per framework.
- Docs: `docs/spec.md` section 12 (the `v-bind()` answer), `publicdocs/03-styles.md` for every feature whose support
  changes.

### 6.1.5 `mf-build` output and exit codes for agents

- Build: the command rules every multifront command follows, first applied to `mf-build`:
  - output: a readable default, quiet when all is fine plus a one-line summary, and `--format json`. One shape for
    every command: file, line, column, end, code, severity, message, plus block and framework when they apply.
    Positions are always in the `.ucf` file, never a generated file.
  - exit codes: 0 clean, 1 findings, 2 bad usage or config.
  - `--help` lists the options with an example; an unknown option names the ones that exist.
  - The shared shape and its readable / JSON printers live where `mf-build` and the M7 commands both reach them
    (core is the likely home: `@multifront/vite` and `@multifront/language-tools` both depend on it). The plan
    settles names and the JSON shape, after comparing what agents already get from `tsc`, `vue-tsc`,
    `svelte-check --output machine` and `oxlint -f json`.
- Deliverable: `mf-build --format json` prints build errors in the shared shape; exit codes and help follow the rules.
- Test: build area, `packages/e2e/build/library-cli.spec.ts`: the real `mf-build` bin on the fixture library, clean
  (exit 0, one summary line), with a clash fixture copy (exit 1, readable and JSON output checked), with an unknown
  option (exit 2, names the valid ones), `--help`.
- Docs: `docs/spec.md` (the command rules), `docs/plan.md` (one line), `publicdocs/06-building-a-library.md`
  (output, exit codes).

### 6.1.6 Milestone 7 plans its commands for agents

  - a planned test per rule that runs the real command on real fixtures.
- Deliverable: the M7 document, ready for its run, with every command agent-friendly by design.
